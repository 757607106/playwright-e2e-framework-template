# 执行、报告与失败诊断

## 验证顺序

先从当前 `package.json` 和配置确认实际脚本与 project。新增或修改测试/适配层后执行：

```bash
npm run quality:ci
npm run test:list
npm test -- tests/e2e/order.spec.ts --project=chromium
```

最后一条是路径示例，替换为实际 spec/project，只执行用户范围内且满足隔离与审查要求的场景。发现列表检查存在性和分类；不能证明业务通过。若真实环境不可用，完成静态检查并列出缺少的环境条件，不运行伪造替代场景。

新增业务适配层的精确清理回调，由本次目标用例与 cleanup 摘要验证，不因此重复运行框架 lifecycle harness。修改资源跟踪/恢复/超时实现，或提取通用 fixtures 并改变其出口依赖时，增加 `npm run test:lifecycle`；它校验四个预期失败，不是普通应用回归失败。通用 probes 必须使用不依赖业务登录的 fixtures，重新组织出口时按 [接入说明](onboarding.md#登录与身份) 核对 harness 导入。

首次验证模板可用 `npm test`；接入真实环境后不要默认全量运行写操作测试。公开发布前执行 `npm run release:check` 并审查文件，不能把启发式扫描视为泄密风险的证明。

## 证据位置

| 位置 | 用途 |
| --- | --- |
| `artifacts/playwright-report/` | HTML 报告，用 `npx playwright show-report artifacts/playwright-report` 打开 |
| `artifacts/test-results/` | 配置保留的 trace、截图、录像等附件 |
| `artifacts/quality-report/` | 场景映射、执行状态和尝试记录 |
| `artifacts/run-data/<runId>/<scopeId>/` | 每次测试尝试的资源账本和清理结果 |

清理摘要也附在测试报告中。按实际存在的文件给出链接；敏感内容仅本地查看，报告和认证状态不进入 Git。区分产品场景和 support 用例。

同一工作目录执行、报告准备和 Allure 生成共用运行锁。不要并发执行这些操作；确需并发使用独立 checkout。发现旧锁时先检查记录的进程是否仍运行；未确认不能删除锁或复制 token 绕过。

## 诊断指定失败

1. 保留原失败，先看指定用例的 trace、DOM、网络、断言和清理摘要。不要以全量重跑作为第一步。
2. 区分脚本缺陷、产品行为错误、环境故障、数据冲突与需求歧义。网络超时不是定位器错误的证据，业务状态错误不能靠放宽期望修复。
3. 仅对证据确认的脚本缺陷做最小改动；运行受影响用例验证。最多三次有证据的修复尝试，仍失败则保留失败并交付原因、证据和下一步条件。

禁止 skip/fixme、`test.only`、固定等待、强制点击、放宽业务断言或吞错使结果变绿。对业务、环境、数据或需求问题不自动改产品代码；如果用户明确要求另行修复，再按新范围处理。

测试主体通过但清理失败仍是失败。查看账本中的已确认 kind/ID 和应用清理适配器；恢复只作用于准确 ID，不扩大删除。超时 callback 可能仍运行，重试前确认实际对象状态，使用幂等且有限时的请求。

## 完成报告

简明报告：实现了哪些场景及覆盖 ID，修改了哪些文件；实际执行的命令、环境名称与结果；HTML/trace/清理证据路径；未解决资源的准确 ID；未验证内容和需要的条件。

只有质量检查和真实目标用例的业务断言、清理均通过，才能说对应业务已验证。flaky、partial、blocked/未执行、本地演示结果分别说明；既有失败不能归为本次通过。发布、推送或通知遵循用户授权，不因测试通过自动扩大任务。
